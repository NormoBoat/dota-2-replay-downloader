# Запуск, жизненный цикл, остановка

Программа работает в Docker или на Linux-виртуалке и крутится, пока её явно
не остановят (`docker stop`, `systemctl stop`, Ctrl+C). Локальная разработка
на Windows тоже должна работать (без Docker-специфики в коде).

## Docker

`Dockerfile`, `docker-compose.yml` и `deploy/collector.service` из прежнего объёма
лежат в `.scope-backup/20261026/`; вернуть по запросу владельца (план ниже в силе).

- `Dockerfile` — multi-stage: `golang:<версия>` собирает статический бинарник
  (`CGO_ENABLED=0`), итоговый образ `gcr.io/distroless/static-debian12:nonroot`.
- `docker-compose.yml`: `postgres:16` (volume `pgdata`) + `collector`.
  - `command: ["run", "-config", "/config/settings.toml"]`
  - volume **каталога** `./config:/config` (не одного файла: запись настроек из
    админки делает `rename`, а на файл-bind-mount он не работает);
  - `restart: unless-stopped` — после сбоя/перезагрузки хоста поднимается сам,
    после `docker stop` — нет;
  - `stop_grace_period: 60s` (по умолчанию 10 с — мало для корректной остановки);
  - `healthcheck: ["CMD", "/collector", "healthcheck"]` — в distroless нет curl,
    подкоманда сама делает `GET /api/v1/health`;
  - `depends_on: postgres` без ожидания: программа сама ждёт БД (см. ниже);
  - в контейнере `api.listen = "0.0.0.0:8080"`, а порт публикуется только на
    хост: `ports: ["127.0.0.1:8080:8080"]`; наружу — через reverse proxy с HTTPS.
- Логи — в stdout, JSON (`log/slog`), Docker их собирает. Секретов в логах нет.

## Виртуальная машина

- Бинарник + `deploy/collector.service` (systemd):
  `ExecStart=/opt/collector/collector run -config /etc/collector/settings.toml`,
  `Restart=on-failure`, `KillSignal=SIGTERM`, `TimeoutStopSec=60`,
  отдельный пользователь `collector`.
- PostgreSQL — свой или внешний, DSN в `settings.toml`.

## Первый запуск

- `collector init -config <путь>` пишет `settings.toml` из значений по
  умолчанию со случайными `secret_key` и `api.token`. Файл уже есть → отказ
  (новый ключ сделал бы токен Steam в БД нечитаемым).
- `collector login -config <путь>` — один раз, если нужен GC-запасной путь.
- `run` без `settings.toml` → понятная ошибка «запустите collector init» и выход.
- `run` сам выполняет миграцию (AutoMigrate идемпотентен); отдельная команда
  `migrate` остаётся для ручного запуска.

## Работа без остановки

- `run` не завершается сам. Единственные причины выхода — сигнал остановки или
  ошибка конфигурации при старте (нет файла, неверный ключ/тип).
- БД недоступна (при старте или потом) → ERROR в лог, повтор с бэкоффом
  (1 с → 30 с), работа продолжается после восстановления. API в это время
  отвечает `503` на всё, кроме `health` (тот показывает `"db": false`).
- Каждый воркер/сессия — в своей горутине с `recover`: паника логируется со
  стеком, компонент перезапускается через бэкофф, остальные не затронуты.
- Нет аккаунта / нет матчей / лимит исчерпан — не ошибка: воркеры спят
  до ближайшего события (`gc_reset_at`, новые матчи), в `status` видно почему.

## Корректная остановка

Сигналы `SIGTERM` и `SIGINT` (`signal.NotifyContext`). Один корневой
`context` на процесс, каждый компонент — дочерний контекст и
`sync.WaitGroup`. Порядок:

1. **Прекратить приём новой работы.** Исполнители не берут новые задачи из `tasks`; API отвечает `503 shutting_down`
   на изменяющие запросы.
2. **Прервать начатое.** Контекст воркеров отменяется сразу: незаконченное
   скачивание не пишется (запись реплея — одна транзакция), запрос к GC в
   полёте прерывается (лимит уже списан). Ждём выхода воркеров до `app.shutdown_timeout`.
3. **Вернуть «захваченное».** Все задачи этого процесса в `running`, которые
   не завершились, — обратно в `queued` без штрафа попытки, `last_error =
   'interrupted by shutdown'`. Восстановление зависших `running` при старте
   (L-07) — страховка на случай `kill -9`.
4. **Выйти из Steam.** Открытая GC-сессия — `LogOff` и закрытие соединения. Токен уже в БД.
5. **Остановить API** — `http.Server.Shutdown` (ждёт текущие ответы, включая
   отдачу реплея, до остатка таймаута).
6. **Закрыть БД** (`sqlDB.Close()`), записать в лог `stopped cleanly`, код выхода 0.

- Общий лимит — `[app] shutdown_timeout = "45s"` (меньше `stop_grace_period`
  60 с / `TimeoutStopSec`, чтобы успеть до `SIGKILL`). Не уложились → ERROR
  `shutdown timeout: workers did not stop` (задачи вернёт восстановление при следующем старте).
- Повторный сигнал во время остановки — немедленный выход (код 130).
- Проверка (L-07): интеграционный тест «нагрузка → SIGTERM» — процесс выходит
  за `shutdown_timeout`, в `tasks` нет строк `running`, нет
  частично записанных реплеев, нет утёкших горутин (`goleak`-подобная проверка
  через `runtime.NumGoroutine` после остановки).

## Изменение настроек из админки

`PUT /api/v1/settings` (см. `05-api.md`):

1. Новые значения валидируются целиком (типы, диапазоны, DSN парсится) — ошибка → 400, файл не трогаем.
2. Запись атомарно: `settings.toml.tmp` → `fsync` → `rename`; предыдущая
   версия сохраняется как `settings.toml.bak`.
3. Применение:
   - `[gc]`, `[downloader]` — сразу, без
     перезапуска: конфиг хранится в `atomic.Pointer[Config]`, компоненты читают
     актуальное значение на каждой итерации (число воркеров загрузчика меняется на ходу);
   - `[database]`, `[api]`, `[app]` — **перезапуск внутри процесса**: та же
     корректная остановка (шаги 1–6, кроме выхода из процесса), затем запуск
     с новым конфигом. Ответ API — `{"restart": true}`; админка ждёт `health`.
   - `[security]` через API не меняется (смена `secret_key` без
     перешифрования сделала бы токен Steam нечитаемым).
4. Комментарии в `settings.toml` при записи из админки теряются
   (TOML-энкодер их не сохраняет); пояснения — в `settings.example.toml`.
